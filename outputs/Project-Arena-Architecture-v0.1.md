# Project Arena｜系统架构与 MVP 路线图

**版本：v0.1 已确认架构基线｜确认日期：2026-09-30**

用户已逐项确认五个问题均采用默认方案，以下据此作为架构基线。本文仅讨论技术选型、模块职责和里程碑，不包含业务代码、接口定义或算法实现。确认架构不等于授权开始编码，也不代表性能或素材授权已经验证。

## 第一步：决策对齐记录（五项均已确认）

| 关键问题 | 选项与取舍 | 已确认方案 |
| --- | --- | --- |
| **1. 优先支持什么设备、同屏多少单位？** | 桌面小规模战斗可优先降低复杂度；手机或数百至上千单位会显著改变性能预算、输入设计和并行策略。 | 桌面浏览器优先；以 **100 个角色＋20 个场地对象**作为首轮压测场景，争取 60 FPS。它是待验证目标，不是性能承诺；弹体与特效另设预算。 |
| **2. 更看重快速做出原型，还是长期扩展机制？** | **Phaser** 是整套游戏框架，场景、输入、物理和动画较齐全；**PixiJS** 专注绘制，需自行组织战斗系统，但更容易保持逻辑独立；**原生 Canvas** 依赖少，却要自建较多渲染与资产设施。 | 选择 **PixiJS＋独立战斗核心**；若工期压倒一切，可切换 Phaser，但保留同样的逻辑边界。React/Vue 只做操作面板，不替代游戏渲染器。 |
| **3. 碰撞希望偏“物理可信”，还是偏“规则可控”？** | **Matter.js** 提供质量、碰撞、反弹，原型风险较低，但群体移动仍需规则层配合；自研简化物理更易约束行为，却要承担碰撞稳定性和穿透问题。 | 使用 **Matter.js 物理适配层＋独立群体分离规则**；允许游戏化调整，不追求科学级仿真，不同时自研第二套碰撞求解器。 |
| **4. 是否必须跨设备得到完全一致的战果？** | 仅本机沙盒主要需要稳定、可调试；严格跨浏览器回放、同步对战则要求从一开始设计确定性数学与物理，成本明显更高。 | Tick 与 Render 强解耦，固定模拟步长并管理随机种子；支持调试复现，但**不承诺跨浏览器逐位一致**，MVP 不做联网和严格回放。 |
| **5. 能否接受混合素材通过统一“棋子外观”呈现？** | 单帧立绘可用朝向标记和程序动画表达动作；真正的全方向角色动画更自然，但需要补绘、限制素材来源或增加美术预算。 | 接受单帧、序列帧混用，以底座、队色、朝向标记统一可读性；不强行旋转所有人形贴图，未获明确授权的素材不进入公开构建。 |

**确认记录：2026-09-30，用户对第 1—5 项均答复“默认”。** 当前采用 PixiJS、Matter.js 与独立战斗核心；Phaser／Vue 仅保留为未来变更的备选，不并行建设。性能测试设备、弹体与特效预算、具体素材清单仍待后续验证。

## 第二步：系统架构设计书

### 2.1 基线技术栈

| 层级 | 基线方案 | 选择理由与边界 |
| --- | --- | --- |
| 工程基础 | TypeScript＋Vite | 类型约束有利于规则扩展；产物是纯静态资源，无运行时后端。 |
| 操作界面 | React | 承担红蓝兵装库、底部机关库、属性面板和控制栏；不逐帧托管战斗实体。已有 Vue 经验时可直接替换，不影响战斗核心。 |
| 战场渲染 | PixiJS，以 WebGL 为发布基线 | 适合精灵、图集、粒子和程序动画；职责清晰。MVP 不依赖 WebGPU，也不假设自带可用的 Canvas 回退。[1] |
| 战斗与物理 | 独立 Simulation＋Matter.js 适配层 | 避免重写基础刚体碰撞；群体分离、目标选择与技能结算仍属于游戏规则。[3] |
| 数据与验证 | JSON＋JSON Schema 校验 | 内容在进入战场前检查结构、引用和规则合法性，而不是战斗中遇错才发现。 |
| 本地存储与发布 | 浏览器本地存储＋GitHub Pages | 对局实时状态放内存；设置与布阵可本地保存、导出。版本化静态资源随构建发布，不依赖第三方素材站在线可用。 |

**为什么暂不选 Phaser：** 它并非无法解耦，而是必须额外约束不要让场景对象承载战斗真相。若选择 Phaser，质量与反弹需求更适合优先评估 Matter，而不是把轻量 Arcade Physics 当作完整刚体系统；两种物理体系不能直接互相碰撞。[2]

**复杂度边界：** MVP 不引入完整 ECS 框架、Worker、多线程物理、通用脚本语言或复杂导航系统；先保留模块边界，在测量出瓶颈后再升级。

### 2.2 模块边界与内存数据流

**配置与资源目录 → 布阵编辑器 → 初始场景快照 → 战斗核心 → 只读状态视图／战斗事件 → 渲染与音频**

玩家操作由应用层转成命令送入对应领域；UI 读取低频摘要，不绕过领域规则直接修改战斗中的单位。

| 模块 | 核心职责 | 不允许承担的职责 |
| --- | --- | --- |
| 应用与编辑器 | 拖拽、选择、面朝方向、布阵校验，以及编辑／运行／暂停／结束的会话状态 | 用画面对象保存唯一的角色属性或战斗状态 |
| 内容目录 | 校验角色、机关、能力、资源引用；提供不可变定义 | 在 JSON 中执行任意脚本 |
| 战斗核心 | 战斗时钟、AI 意图、技能、伤害、Buff、触发与胜负规则 | 依赖 React、DOM、音频或贴图是否加载完成 |
| 空间与物理适配 | 质量碰撞、位移、反弹、碰撞过滤，以及空间查询服务 | 直接决定扣血、阵营或技能效果 |
| 表现层 | 将状态绘制为精灵，消费事件播放 Tween、特效、音效 | 根据动画进度或像素位置反向裁定命中 |
| 存档与诊断 | 布阵快照、内容版本、随机种子、事件摘要与性能指标 | 将浏览器存储当作逐 Tick 数据总线 |

**Tick／Render 的约束：**
- Tick 使用固定模拟步长；Render 根据浏览器刷新绘制并插值。帧率下降不能改变技能计时或伤害数值。
- Simulation 是战斗状态的唯一权威；运动由其物理适配层推进，不让物理引擎、UI 与 Tween 同时争夺真实坐标。
- 攻击、命中、死亡等事件触发表现；暂停、单步及慢速观看控制模拟时钟，而非依赖动画完成回调推进战斗。
- 开战从布阵快照创建独立世界；重置丢弃运行态并恢复初始布阵。MVP 开战后锁定编辑，不混入实时增删单位。
- 页面失焦默认暂停；过载时限制表现并提示，不无限追赶后台积压时间，也不跳过关键结算。
- 固定步长与随机种子是复现的必要基础，**不是严格确定性的保证**。跨平台一致性若成为硬要求，须重新评估物理方案。

### 2.3 实体、Tag 与 Buff：轻量 ECS 思路，避免继承树

采用“**实体标识＋组件数据＋集中系统**”的组合模型，但不为 MVP 引入重型 ECS 框架。角色、陷阱、地形、设施和弹体共享必要能力，不建立不断加深的角色子类树。

- **组件按职责分组：** 空间与碰撞、生命与阵营、移动与目标、攻击与技能、触发与效果；外观引用独立于战斗属性。
- **Tag 是声明，不是自动生效的代码：** 已注册的能力系统解释标签。飞行影响哪些地形、碰撞和受击规则必须显式约定，不能等同于“无视一切”；重甲由伤害修正处理；狂暴由条件触发和属性修正处理。
- **Buff 是有生命周期的效果实例：** 来源、持续、叠加、刷新、互斥与解除由统一效果系统管理；不在各角色逻辑中分别处理。
- **技能由可复用能力组合：** 目标筛选、形状判定、伤害、位移和效果施加相互独立。不同外观的技能不应复制一套结算逻辑。
- **连锁反应有受控边界：** 炸药桶连爆、反伤和死亡触发遵循统一事件顺序与连锁预算，避免无限递归或重复结算。

**JSON 驱动的真实边界：** 在已有能力集合内新增角色或陷阱，可以只新增配置与资源；出现新的机制原语时，仍需要扩展系统。不要承诺“任意新玩法都只写 JSON”。Cost 在 MVP 仅作展示元数据，不参与预算、购买或经济循环。

### 2.4 空间、物理与场地互动

- **自由摆放采用连续的世界坐标。** 可以按逻辑像素理解，但不能绑定实际屏幕像素；缩放、窗口大小和高 DPI 不改变碰撞结果。开战前检查越界与非法重叠。
- **碰撞体与贴图解耦。** 大立绘不等于大体积；质量、碰撞尺寸和渲染尺寸独立管理。
- **硬碰撞与软分离分工。** 物理层解决实体占据空间及墙体接触；群体规则提供分离意图。单位受击退时，寻敌移动不得立即覆盖击退；具体优先级在下一轮定稿。
- **360 度击退由模拟驱动，撞墙反弹由物理处理。** Tween 只做倾斜、压缩、闪白等附加表现，绝不模拟真实击退位置。
- **技能判定独立于身体碰撞。** 统一支持扇形、直线穿透和圆形 AoE；筛选阵营、飞行层、遮挡与同次命中的重复结算规则集中管理。
- **地形与机关复用触发—效果体系。** 熔岩是持续区域伤害，传送带／弹簧板施加运动效果，炸药桶／地刺触发伤害与击退；炮台组合寻敌和攻击，祭坛施加 Buff。中立对象有明确敌我与受益规则，不能靠颜色推断。

MVP 以简单边界场地为主，不承诺复杂迷宫寻路；飞行只是二维规则分层，不引入完整高度物理。高速弹体穿透、群体挤压和墙角卡死列为早期验证场景。

### 2.5 异构资产适配与加载

**核心原则：统一游戏中的表现契约，不强求所有原始素材具有相同像素规格。**

1. **资源登记与授权先行。** 每项资源登记来源、作者、许可、署名、修改与公开分发条件；缺授权证据的资产不能进入公开构建。代码许可与素材许可分别管理。
2. **统一外观描述。** 每个资源适配器说明视觉尺寸、锚点、落脚位置、朝向能力、动画能力与采样风格；物理尺寸另行定义。像素图与高清立绘保留各自采样策略，不强制粗暴拉伸。
3. **按能力降级。** 单帧立绘提供待机浮动、攻击前倾、受击闪白、死亡淡出；序列帧复用同一套表现事件。缺动画可降级，缺图片有占位，但技能范围与朝向仍必须清楚可见。
4. **用统一视觉标识建立一致性。** 底座、红蓝队色、血条、朝向箭头、范围预警承担战术识别；不通过给缺少方向帧的角色硬转整张人形立绘解决所有朝向。
5. **加载分层。** 先校验配置和引用，再准备 UI、当前布阵必需资源，其他内容按需加载。配置错误阻止开战；非关键表现缺失可以降级并提示。资源预算同时考虑下载量与解码后的纹理内存。
6. **音频是表现服务。** 统一音量、并发和优先级，避免连锁爆炸叠音失控；用户交互后启用音频，静音或播放失败不影响模拟。

| 来源 | 纳入策略 |
| --- | --- |
| **Kenney** | 官方素材页的游戏资产采用 CC0，可作为 UI、机关和占位资源的首选；保留随包许可。[5] |
| **Itch.io：0x72、Pixel Frog；OpenGameArt；Pipoya；Sora／白螺子屋** | 逐具体素材包核验，不能将平台、作者名或“免费”视为统一开放许可。确认是否限制引擎、改图、署名和再分发，再完成对应外观适配。 |
| **东方 Project／MUGEN 同人图素** | 同人可下载不等于可再次使用。东方指南明确禁止直接提取官方游戏素材，以及未经作者许可使用他人同人作品；浏览器同人游戏须免费游玩。MUGEN 是生态而不是许可证，逐资源核实权利链，来源不明或疑似商业游戏拆包的图素不纳入。[6] |
| **魔王魂、M-art** | 音频许可与图片许可独立审核。魔王魂不是 CC0；按选定许可路径满足署名等条件，游戏内使用与原始音频再分发分别核查。M-art 未指定具体曲目与许可页，本稿不作统一授权判断。[7] |

**公开发布底线：** GitHub 仓库、构建附件和网页实际送达的素材都要纳入许可检查。图集、压缩或混淆不能使未经许可的分发变成合法分发。

### 2.6 GitHub Pages 与 MVP 边界

发布的是完成构建的静态文件，运行时不需要服务器进程。所有配置与资源路径适配仓库子路径；MVP 使用单页面状态切换，有路由需求时优先避免依赖服务器回退的路径模式。[4]

不依赖运行时跨站抓取素材，不保存密钥，不承诺防作弊；浏览器本地存档可丢失且不自动跨设备同步。“无后端”不等于首次访问即可离线使用，完整离线缓存留待后续。

**本轮不做：** 经济系统、关卡流程、联机、账号云存档、严格确定性回放、完整 Mod 脚本、复杂寻路、全角色多方向补帧。

## 第三步：四阶段项目计划书

| Phase | 里程碑目标 | 必须通过的验收门槛 |
| --- | --- | --- |
| **1．架构骨架与灰盒验算** | 建立静态部署、独立 Tick／Render、物理适配和诊断；使用简单几何体完成自由布置、质量碰撞、软分离、击退与撞墙反弹。锁定目标设备、浏览器及性能预算。 | GitHub Pages 子路径可运行；改变画面刷新率不改变模拟计时；无渲染也能执行逻辑测试；两种质量对象、密集挤压、墙角和高速运动场景通过检查。性能目标以实测调整，不先验宣称达标。 |
| **2．最小可玩对战闭环** | 红蓝兵装库、拖拽与朝向、开始／暂停／重置；实现近战、扇形、穿透直线、圆形 AoE 的代表角色；完成寻敌、攻击、死亡、基础 Tag／Buff。 | 玩家能从空场完成一局并重置；低帧率下伤害和技能计时正确；明确处理双方同时死亡、无可攻击目标和超时僵局。已有能力的新角色只需新增配置与资源。 |
| **3．机关与异构素材整合** | 底部机关库接入熔岩、传送带、弹簧板、炸药桶、地刺、炮台和祭坛；完成单帧／序列帧适配、程序动画与基础音频。 | 群体击退、陷阱连锁、飞行与地形、护甲与 Buff 组合可解释且无无限触发；缺失资源有可见降级；替换素材不改变碰撞或伤害结果。 |
| **4．MVP 收敛与公开发布** | 完成本地布阵保存／导出、必要的新手说明、内容校验、素材署名、生产构建检查和性能回归。 | 在 Phase 1 约定的设备与规模下达标；连续运行及反复重置无明显资源增长；没有已知的重复伤害、永久卡死或关键资源缺失；公开资源逐项完成授权检查。 |

**已完成：规模方向、复现要求、渲染路线、物理路线与素材表现标准的确认。后续顺序：先证明战斗闭环可靠，再扩大内容与美术库。**

下一阶段优先验证 Phase 1 灰盒与物理风险，但本次只确认和更新文档，未开始开发、安装依赖或部署。继续遵守仅讨论高层架构的约束，不展开组件字段、接口、公式、碰撞算法或业务代码。
